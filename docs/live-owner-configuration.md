# Configure the TEST gateway

Start with the read-only baseline and the OAuth gate. Use the [acceptance runbook](live-acceptance-runbook.md) for the live sequence, [evidence record](live-acceptance-evidence.md) for the current results, and [rollback procedure](live-activation-and-rollback.md) for the setting changes and stop conditions. The approved source delivery has a zero agent-execution budget. Production activation is a separate decision.

## 1. Choose where to run the live checks

| Option | Setup | Trade-off |
| --- | --- | --- |
| **Use an approved operator workstation or runner** | Use a machine with direct HTTPS access to the approved TEST origins and the existing Azure operator and workspace admin sessions. Retain private evidence there and share the sanitized outcomes. | Usually the fastest route. An operator needs to run the interactive and live probe steps. |
| **Use a dedicated Codex Cloud task** | In that task's Cloud settings, allow the exact TEST host and the required approved identity and management destinations. Bind the scoped Azure identity through the environment's identity configuration when offered. For interactive work, use a task with desktop control and sign in through the take-over surface. | Lets the task run more of the setup. The probe requires direct HTTPS and disables proxies for credentialed requests, so verify that the configured runner can reach TEST directly. |

1. Ask the Azure operator to confirm the subscription, TEST resource group `rg-niobium-agents-test`, Function App `niobiumagents-func-test`, region West US 2, application Table account `niobiumagentsstdtest`, host account `niobiumagentsststest`, and vault `niobiumagents-kv-test`. These are the repository's expected names.
2. Resolve the actual default hostname through the scoped Azure account. Record it and any approved custom ingress in the restricted manifest. A Function App name alone does not identify its default hostname.

```sh
az resource show --resource-group rg-niobium-agents-test \
  --name niobiumagents-func-test --resource-type Microsoft.Web/sites \
  --api-version 2024-11-01 --query properties.defaultHostName \
  --output tsv --only-show-errors
```

3. Use a resource-group Reader for resource metadata, a scoped monitoring reader for the TEST Logs workspace, and Storage Table Data Reader on the application data needed for inventory. Have the existing operator export only the allowed booleans, authentication policy, CORS, and Key Vault reference status if the reader cannot inspect those directly. Have the operator record the actual production flags separately. The deploy identity in GitHub Actions belongs to its workflow.
4. Compare exact-commit GET `/health` with the latest successful deployment. Record flags, current native key policy, pending jobs, active trials and intended rollback before a configuration change. Use the approved origin from step 2. [Expected resource names](../README.md#azure-naming-and-resources)

## 2. Prepare the Entra resource and ChatGPT OAuth client

1. In **Microsoft Entra admin center > App registrations**, select the approved TEST API registration or create a single-tenant TEST registration if the tenant owner confirms none exists. Record its tenant ID and application client ID privately. Configure the resource to issue v2 access tokens and note its OpenID Connect discovery endpoint. The gateway validates the tenant-specific issuer at `https://login.microsoftonline.com/<tenant-id>/v2.0`.
2. In **Expose an API**, review the **Application ID URI** and add the enabled delegated scope `AgentGateway.Dispatch`. Use the tenant's agreed consent policy and a clear description of the permitted gateway actions. The scope requested by the client is the resource URI plus `/AgentGateway.Dispatch`. Verify the actual access-token `aud` separately and use its exact value in both the App Service and application configuration.
3. In the approved ChatGPT workspace, open the app or custom MCP setup for the TEST gateway. Use the resolved origin plus `/runtime/webhooks/mcp` and OAuth. Inspect the actual registration mode, redirect URI and supported client authentication shown by the workspace. Keep the connection restricted to the acceptance users.
4. Where the workspace supports a predefined client, configure its Entra registration with that exact redirect and supported client authentication. In its **API permissions**, add only the approved delegated gateway scope and have the consent owner review it. If the chosen mode needs a client credential, enter it only in the authorized secret or connector configuration. Keep private credentials out of GitHub, the shared record and chat.
5. Record the approved connector client ID, single tenant, exact issued-token audience, and expected delegated scope. The gateway derives identity from the signed issuer, tenant, object ID and authorized client. The two intended agent connections must yield distinguishable validated identities. [Expose a Microsoft Entra web API](https://learn.microsoft.com/en-us/entra/identity-platform/quickstart-configure-app-expose-web-apis) · [ChatGPT OAuth registration](https://developers.openai.com/plugins/build/auth)

**Client choice.** Prefer the predefined Entra client if the actual ChatGPT flow supports it. Entra does not offer dynamic client registration. If the workspace requires a different registration mode, pause enrollment and record the exact compatibility issue. A reviewed OAuth intermediary is a separate design choice with its own issuer and token-boundary review. Keep the single-tenant and audience rules while evaluating that option. [Azure MCP authorization](https://learn.microsoft.com/en-us/azure/app-service/configure-authentication-mcp)

## 3. Prepare the health identity and reviewed transition

1. **Recommended** - create a dedicated app-only TEST verifier using workload federation. In the TEST resource's **App roles**, define an application-only permission such as `Gateway.Health.Read`. In the verifier's **API permissions > Add a permission > My APIs**, assign just the application permission and have the tenant owner review consent and assignment. Identify the workload's exact approved repository, environment and federated subject. The verifier does not need agent grants, a Workspace Agent API token, or a delegated scope.
2. Confirm how the resource and ingress restrict that caller. For App Service authentication, review `defaultAuthorizationPolicy.allowedApplications` and, if used, `allowedPrincipals.identities`. Those lists use client IDs and principal object IDs respectively. Including both requires callers to meet both conditions. Review which application tokens Entra may issue for the resource. Assigning a role in Entra alone does not create a route-level role check in the gateway. Prove that the app-only token can access health and is denied on a delegated MCP tool.
3. **Alternative** - use the existing TEST deployment federated application temporarily with only a health app permission for this resource. This reduces setup, but puts verifier and deployer in the same identity's audit trail. Use a separately scoped token and retain the independently checked-out harness. A dedicated verifier gives clearer separation.
4. Coordinate the reviewed workflow change with the maintainer. The opt-in verifier already accepts an environment-only token and checks exact-commit ready plus anonymous denial. The current trusted workflow still uses scaffold mode. Stage credential acquisition and `--require-authentication` for the candidate and independent health checks. Keep the main-pinned harness and required status checks. If the controller rejects the revised workflow identity, follow the repository's documented administrator activation procedure before changing live ingress.
5. In the reviewed runner, use the approved verifier login and request a short-lived token for the exact resource's `/.default` scope. Supply it as `READONLY_API_ACCESS_TOKEN` only to the verifier process. Set `READONLY_API_URL` to the approved origin and `READONLY_EXPECTED_COMMIT` to the deployed SHA. Disable shell tracing around acquisition and omit token values from reports. The command and required check are in the [runbook](live-acceptance-runbook.md#gate-1---oauth-and-authenticated-health). Reconfirm the trusted status on a subsequent feature SHA after the reviewed transition. [App roles](https://learn.microsoft.com/en-us/entra/identity-platform/howto-add-app-roles-in-apps) · [App Service validation](https://learn.microsoft.com/en-us/azure/app-service/configure-authentication-provider-aad#configure-additional-checks) · [Protected workflow changes](pr-approval-handoff.md#deployment-workflow-changes)

## 4. Protect ingress and prove the actual connection

1. Apply the reviewed TEST auth configuration once protected verification is ready. Use `infra/gateway-auth.bicep` as the baseline and review the exact tenant, resource client ID, issued audience, authorized clients and any metadata exception. Require HTTPS and authentication with a 401 challenge for anonymous requests. Keep the native MCP system key requirement during the dual-gate trial. Review any portal auto-configuration because it can also change that requirement.
2. If using App Service's preview protected-resource metadata support, configure `WEBSITE_AUTH_PRM_DEFAULT_WITH_SCOPES` to advertise the full approved delegated scope. Inspect the resource and issuer advertised via the exact OAuth challenge, and compare discovery against what ChatGPT requests. Limit public paths to the reviewed discovery metadata. Verify each raw or custom execution and health origin separately.
3. Project the actual `GatewayAuthenticationOptions__TenantId`, `Audience`, `AllowedClientIds__0` and `RequiredScope` settings and trusted `AgentGatewayOptions__InternalWorkspaceKey`. Configure further allowed client entries only for reviewed delegated test clients. Keep the app-only verifier out of the delegated MCP allowlist. Use reviewed environment-specific configuration so a feature push cannot silently erase the approved state.
4. In a registry-only window, verify that no enabled registration/grant pair can dispatch, that tracked access and starts are off, and that the timer is off. Supply the approved credential alias needed by the configuration validator. Load the delegated and app-only test tokens and the native key into the probe only through the approved secret mechanism. Confirm that each negative token isolates its intended condition. If an isolated wrong-tenant or unauthorized-client token cannot be issued through policy, record that live case as pending and retain the narrow tenant configuration.
5. Run `scripts/probe_gateway_auth.py` from the approved runner against each approved TEST origin. Check denied OAuth with the key present, key denial with a valid bearer, positive read-only listing, discovery of six tool schemas, and no identity carryover through a session ID. Save only the sanitized check output and rejection layer.
6. In the actual approved ChatGPT connection, prove login, consent, read-only `list_agents`, refresh or reconnect, and distinct A/B principals. If the product cannot send a native key, obtain the reviewed TEST-only transition after the dual-gate proof. Keep mandatory OAuth and repeat the execution-ingress checks when switching. [Probe inputs](protected-gateway-acceptance.md#operator-inputs) · [ChatGPT OAuth](https://developers.openai.com/plugins/build/auth)

## 5. Stage storage, secrets and A/B

1. In the reviewed TEST change, use `infra/tracked-jobs.bicepparam` to stage `AgentJob` and `AgentMaintenance`. Use `infra/parent-continuation.bicepparam` later if that gate needs `AgentContinuationRoute`. Check the actual app data endpoint, runtime managed identity and table permissions. Use the approved operator with scoped Table Data Contributor access only for conditional configuration writes.
2. In ChatGPT's Workspace Agent builder, limit A and B to the approved users and the tools required by their respective jobs. Use separate verified accounts for the intended connections. An agent-owned connection is shared, so choose a dedicated approved account and constrain its permissions and sharing. Use B's **Add channel > API** and record the approved `agtch_...` identifier in the restricted manifest. Use **ChatGPT Admin > Access token** with the **Workspace Agents** scope. Store the token through the existing TEST Key Vault path. [Agent tools and API channels](https://help.openai.com/en/articles/20001143-chatgpt-workspace-agents-for-enterprise-and-business)
3. Project the upstream alias through `APPSETTING_KV_AgentGatewayOptions__CredentialAliases__<alias>`, and independent approved keys through `APPSETTING_KV_TrackedJobOptions__IdentityKey` and `APPSETTING_KV_TrackedJobOptions__SigningKeys__<version>`. Set `APPSETTING_TrackedJobOptions__ActiveSigningKeyVersion` for the active version. Verify reference resolution without exposing values. Preserve the stable identity key and prior signing versions through outstanding capability expiry.
4. Derive each opaque principal using `CallerContext.FromValidatedClaims` with the validated workspace, issuer, canonical tenant GUID, `oid:<lowercase-object-guid>`, lowercase authorized client ID and confirmed dispatch scope. Use `AgentGrant.PartitionFor(caller)` for the grant partition. Use the component's existing implementation.
5. Configure the B registration as version 2 with `result_schema: agent-result.v1` and `result_writer_principal_key` for validated B. Give A's version-2 grant only `can_start_job` and B's only `can_submit_result` for that alias. Stage these disabled. Use `scripts/configure-agent-registry.sh` with reviewed files outside the checkout. Set `expected_e_tag` to null on create and the exact current ETag on update. Verify the write receipt and read-back before enabling the intended grants in the approved window. [Registry command](configuration-and-development.md#operator-registry-command) · [Tracked jobs](tracked-jobs.md)

## 6. Decide how far to run the trials

| Decision | Recommended minimum | Further option and implications |
| --- | --- | --- |
| **Initial execution** | Run one store-only synthetic case, with one A invocation and at most one B trigger attempt. Explicitly set the trial's `MaxDispatchAttempts=1`. Use 6 × 7 and a synthetic marker. Keep observation, parent and timer off. | Additional cases consume separate scope and time. Prefer isolated tests for races and failure branches. An uncertain send is held for reconciliation. |
| **Provider observation** | Keep it off until store-only passes. Later approve one separate fixture with a short time window and a cap on GET observations. Stop the worker at the approved cap or terminal status. | Enables beta metadata and periodic reads. Inventory older jobs first and account for existing due work. |
| **Parent continuation** | Keep it off until explicitly needed. For a trial, use one approved API conversation and one expiring route. Budget the A API bootstrap, B submission and A notification separately, with at most one attempt each. | Adds a live invocation after B's callback. Review the parent channel, exact conversation key, registration/grant and both reuse settings. A UI chat link cannot bind the route. |
| **Retention and production** | Use the existing reviewed TEST deadlines and retention unless the operator identifies a business need to revise them. Leave production activation for a decision based on live TEST results and rollback evidence. | Before any change, record its exact policy, the key retention needed for issued jobs and who reconciles unresolved sends. |

Record the approved trial window, dollar ceiling, allowed retry behavior, maximum starts and observations, operator and rollback owner in the restricted scope record. Reconcile all pending and ambiguous jobs and events after the trial. Use synthetic telemetry markers and record a positive ingestion control before claiming privacy.
